01

平台概览

Arenyxa 被设计成一个技术平台，而不是单一用途的代理工具或抓包查看器。

传统网络分析往往需要在抓包工具、HTTP 代理、临时脚本、API 客户端、浏览器开发者工具和独立自动化系统之间来回切换。Arenyxa 的目标是在保持各引擎模块化的同时，把这些工作流整合到统一的技术操作模型中。

OBSERVABILITY

理解真正经过网络链路的数据。

抓取流量、识别会话、解析协议行为，并保留后续调查需要的证据与上下文。

INTERCEPTION

在授权条件下检查应用行为。

通过受控拦截完成调试、请求分析、协议检查与 MITM 测试。

OPERATIONS

把一次性分析转化为可重复流程。

扩展到健康检查、自动化、压力测试、恢复与运行验证。

02

设计原则

模块化、权限边界分离与运行韧性，是 Arenyxa 的核心工程约束。

01

界面模式不能等同于权限。

体验模式只负责改变界面与工作流呈现；高风险能力仍由身份、策略、完整性与授权检查独立控制。

02

核心引擎应保持可独立测试。

抓包、MITM、协议分析、存储、安全、恢复和自动化可以独立演进，而不是被迫捆绑成难维护的单体。

03

优先采用有界并发。

性能优化必须可测量、可恢复、可预测，避免通过盲目增加 worker 数量换取短期吞吐。

04

完整性与恢复属于生产能力。

健康诊断、清单校验、修复路径、审计与故障处理属于平台架构，而不是发布之后的补丁。

03

核心能力

独立引擎通过共享分析工作流连接起来。

平台围绕真实的网络调查生命周期组织：获取流量、理解协议、检查应用行为、关联证据、自动化可重复操作，并围绕高权限行为维持清晰的控制边界。

14

工程边界

专业工具应明确它优化什么，也应明确哪些边界不能被模糊。

授权

拦截、调试与安全测试应仅用于操作者有权分析的系统与流量。

权限

体验模式、导航可见性和许可证不能替代 Root 身份认证、完整性或企业策略。

性能

更高吞吐不能以无控制并发、饥饿或不可恢复运行状态为代价。

恢复

修复只有在恢复状态被验证后才算完成，而不是文件复制结束就算成功。

ENGINE DEEP DIVE

Engine-level responsibilities and boundaries.

Arenyxa becomes maintainable only when every engine owns a clear responsibility. Capture acquires traffic; protocol intelligence interprets it; security authorizes actions; recovery validates restored state.

Capture Engine

Owns packet acquisition, session construction, filtering inputs, capture lifecycle and evidence-oriented handoff. It should remain independent from UI navigation and high-level authorization policy.

  • Packet / flow acquisition
  • Session context
  • Capture lifecycle
  • Evidence handoff

MITM Engine

Owns controlled interception, TLS-aware application inspection, stream lifecycle and request/response manipulation within authorized environments.

  • TLS negotiation context
  • HTTP inspection
  • WebSocket streams
  • Replay-oriented state

Protocol Intelligence

Transforms packets and streams into semantic structures, relationships and investigative cues. Its output should explain behavior rather than merely expose raw fields.

  • Decode
  • Flow correlation
  • Protocol semantics
  • Anomaly cues

Automation Engine

Executes repeatable procedures with explicit cancellation, bounded concurrency, failure propagation and verifiable completion criteria.

  • Task orchestration
  • Batch execution
  • Timeouts
  • Validation

Security Kernel

Owns security-sensitive decisions independently from the workspace that exposes a feature. Navigation visibility can never substitute for actual authority.

  • Identity
  • Policy
  • Integrity
  • Authority

Recovery & Health

Detects degraded state, validates manifests, restores trusted assets and verifies post-repair behavior before declaring recovery complete.

  • Health checks
  • Repair manifests
  • Integrity verification
  • Recovery validation

ENTERPRISE MODEL

Enterprise is an operational context, not a privilege bypass.

Enterprise functionality should be projected through identity, enrollment, administration and policy. The interface can expose enterprise tools, but protected actions continue to depend on the underlying authority model.

01

Enterprise Identity

Represents organization-aware identity and enrollment state separately from visual mode selection.

02

Local Super Admin

Provides managed local administration without replacing Root Developer technical authority.

03

Identity Vault

Local encrypted identity state can preserve enrollment, administrative metadata and authority relationships.

04

Enrollment Code

Controlled enrollment supports explicit onboarding rather than silently trusting an external enterprise context.

05

Pending Enrollment Queue

Unapproved enrollment requests remain pending until an authorized administrator makes a decision.

17

ROOT DEVELOPER

Highest technical authority with non-bypassable security checks.

Root Developer is intended for deep engineering, debugging and recovery. Once the Root session is valid and authentication/integrity checks pass, product licensing, experience mode and role presentation should not block access to technical capabilities. The Root authentication and integrity checks themselves remain mandatory.

Device / Root key→Authentication→Integrity verification→Validated Root session→Full technical authority

Root authority ≠ UI selection

Choosing a Root workspace requests presentation state. It does not create authority.

Product gates do not outrank Root

After security-critical checks pass, licensing and experience gates should not hide technical features from Root Developer.

Integrity remains mandatory

Root Developer must not bypass the checks that establish the authenticity of the Root session itself.

Developer Authority Utility

Offline key issuance, renewal, revocation and backup workflows should keep private authority material local.

PERFORMANCE & CONCURRENCY

Performance is a controlled systems-engineering problem.

Arenyxa favors adaptive concurrency, bounded queues, explicit timeout boundaries and observable runtime state. Stable throughput matters more than creating the maximum number of workers.

ConcernFailure modeEngineering response
Host concurrencyStarvationPer-host coordination and bounded waiter behavior
Background executionUnbounded task growthWorker limits, cancellation and lifecycle ownership
Network operationsIndefinite stallsExplicit DNS / TCP / TLS / connect timeout boundaries
StorageLock contentionLocal SQLite by default; PostgreSQL path for heavier concurrency

RELEASE ENGINEERING

Release readiness is a chain of evidence.

Producing an executable is not the definition of a successful release. Source integrity, test results, packaging behavior, runtime smoke checks, repair assets and CI all need to agree on the same release candidate.

Source manifest→Unit & contract tests→Stress validation→Build→Package→Install→Smoke test→CI green

SOURCE_MANIFEST.sha256

Provides a reproducible integrity reference for release source material.

Repair manifest & seed

Recovery assets should match the intended trusted baseline and remain verifiable.

Quality gates

Architecture, security, runtime, performance and packaging gates reduce single-test blind spots.

GitHub Actions

A release candidate should not be considered complete while required CI jobs remain red.

PLATFORM DIRECTION

Windows-first stability before broader platform expansion.

The current engineering direction prioritizes a stable, complete Windows product before widening the platform matrix. This keeps validation focused while architecture, security and runtime boundaries are still evolving quickly.

Windows primary target

Desktop UI, capture, MITM, developer mode, enterprise workflows, packaging and recovery are validated first on Windows.

Linux follows stability

Cross-platform expansion should happen after core contracts are mature enough to avoid duplicating unresolved platform defects.

CLI remains first-class

Platform expansion should not make GUI the only operational surface; direct terminal workflows remain part of the product architecture.

Modular growth

New capabilities should integrate through stable engines and contracts rather than replacing mature subsystems without necessity.
