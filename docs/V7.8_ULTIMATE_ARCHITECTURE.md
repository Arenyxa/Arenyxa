# Arenyxa v7.8 Ultimate Architecture

## 1. 目标与不变量

本次稳定化保留 Arenyxa v7.8 的既有 API、采集引擎、协议引擎、企业运行时和恢复能力。改造边界集中在权限解析、页面生命周期、启动壳、运行时监督、数据库可观测性和协议元数据能力。

以下不变量是实现与测试的共同约束：

- Experience Mode 只描述界面复杂度，不授予安全权限。
- Runtime Mode、Account Role、Developer Authority、Active Root Session 独立求值。
- Root Credential 不是 Root Session；只有已认证、未过期、未撤销且含 `platform.root` capability 的进程内会话可触发 `SHOW_ALL`。
- Root Session 不进入 `AppSettings`，不持久化到 `settings.json`。
- 页面在权限检查成功前不得构造；Preset 切换不清空页面缓存。
- Qt 主线程只应用导航差异和创建 UI 骨架；持久化、数据页加载和重型刷新使用后台任务。
- 启动、Root challenge、恢复提示和主工作区共享一个 `ArenyxaShellWindow`。

## 2. Navigation Capability Architecture

实现目录：`src/arenyxa/navigation/`

| 文件 | 职责 |
| --- | --- |
| `models.py` | 五维上下文、Manifest、Decision、Diff 的纯模型 |
| `manifest.py` | 内置页面的声明式权限清单 |
| `registry.py` | 线程安全的 Manifest 注册表与扩展入口 |
| `resolver.py` | 无副作用、确定性的访问决策和导航差异计算 |
| `guards.py` | UI 路由和 deep-link 共用的 fail-closed guard |
| `factory.py` | 运行时上下文投影与权限检查后的惰性页面工厂 |

### 2.1 五个独立维度

`NavigationContext` 由以下维度组成：

1. `ExperienceMode`: `GUIDED`, `ADVANCED`, `DEVELOPER`
2. `RuntimeMode`: `DESKTOP`, `SERVER`, `WORKER`
3. `AccountRole`: `PERSONAL`, `ENTERPRISE_MEMBER`, `ENTERPRISE_ADMIN`, `LOCAL_SUPER_ADMIN`
4. `DeveloperAuthority`: credential 是否已验证、有效、未撤销、未过期，以及其 capabilities
5. `ActiveRootSession`: 当前进程内 Root 会话状态及 `platform.root` capability

额外的 `capabilities` 集合用于页面的细粒度声明，不替代任何一个维度。

### 2.2 求值顺序

```text
Page ID
  -> Manifest exists?
  -> Active Root Session?       -> allow / SHOW_ALL
  -> Root-only check
  -> Experience Mode check
  -> Runtime Mode check
  -> Account Role check
  -> Developer Authority check
  -> Required capabilities check
  -> allow
```

任何失败均产生稳定的拒绝原因，例如 `RUNTIME_MODE_MISMATCH`、`ACCOUNT_ROLE_REQUIRED` 或 `DEVELOPER_AUTHORITY_REQUIRED`。按钮可见性与实际路由调用同一个 resolver，因此隐藏按钮不是权限边界。

### 2.3 关键隔离规则

| 上下文 | Enterprise | Server Admin | Developer Tools |
| --- | ---: | ---: | ---: |
| Personal + Advanced + Desktop | 否 | 否 | 否 |
| Enterprise Admin + Desktop | 是 | 否 | 否 |
| Developer Experience、无 Authority | 否 | 否 | 否 |
| Developer Experience、有效 Authority | 否 | 否 | 是 |
| 有效 Active Root Session | 是 | 是 | 是 |

## 3. 页面生命周期与 Preset 切换

`MainWindow` 启动时只创建首个可访问页面。路由顺序为：

```text
Navigation Resolver
  -> Guard
  -> Page Factory
  -> create UI skeleton once
  -> add to QStackedWidget
  -> activate on next event-loop turn
```

`PageFactory` 保留已经创建的页面。权限变化只修改导航可见性；被移除的页面不会被销毁，重新允许时直接复用。最终关闭时才释放缓存引用。

Preset 切换采用异步准备：

```text
User selection
  -> update in-memory Experience preference
  -> background persist + calculate NavigationDiff
  -> generation check
  -> apply added/removed/updated visibility only
  -> route to the new landing page
```

记录指标为 `context.navigation_metrics["preset_switch_latency_ms"]`。纯 resolver 的性能门槛覆盖 Guided → Advanced `<300ms`、Advanced → Developer `<500ms`、Root Unlock `<800ms`、Root Logout `<500ms`。

## 4. Single Window Startup Architecture

`ArenyxaShellWindow` 是正常启动期间唯一的顶层窗口，内部 `QStackedWidget` 包含：

- `SplashPage`
- `AuthenticationPage`
- `RecoveryPage`
- `MainPage`

主流程为：

```text
Process Start
  -> environment/runtime check
  -> show ArenyxaShellWindow/SplashPage
  -> bootstrap services
  -> optional Root Authority Challenge
  -> construct MainWindow as a child widget
  -> MainPage
```

MainWindow 在 Root challenge 完成前不构造，并从构造开始就以 `MainPage` 为 parent，避免短暂成为顶层窗口。Root 认证失败不会退出应用；认证页显示失败状态并允许继续普通会话。

Root challenge 明确呈现 Device Identity、TPM Status、Challenge Fingerprint 和 Verification State。凭据验证成功后，现有 Developer Access Manager 创建短期进程内会话；退出、过期或撤销立即回收 Root 导航覆盖。

检测到 crash marker 或恢复到中断运行状态时，Shell 显示 `Unexpected shutdown detected`、Previous task、Previous capture 和 Previous state，用户确认后在同一窗口进入主工作区。

## 5. 稳定性与数据库

`ArenyxaRuntimeSupervisor` 在独立守护线程中监督 UI Thread、Async Loop、Worker、Database 和 Capture Engine 的 heartbeat/probe。UI event loop 超过 5 秒未 heartbeat 时：

- 使用 `faulthandler` 捕获所有线程栈；
- 写入有界 JSON 状态与 stack 文件；
- 记录稳定错误码 `EVENT_LOOP_BLOCKED`；
- 内存中最多保留 128 个 incident。

SQLite 稳定性增强包括 WAL 大小监控、阈值触发的 PASSIVE checkpoint、`quick_check` corruption detection、ping 和慢查询日志。慢查询日志只记录操作类型与 SQL identity hash，不记录 SQL 内容或参数。

PostgreSQL 企业运行时继续使用 `pool_pre_ping`/Psycopg pool，并增加连接重试策略、health snapshot 和 commit/rollback transaction trace。trace 记录 backend、耗时、statement count 和非敏感 identity，不记录 DSN、SQL 或参数。

## 6. 协议智能

既有 HTTP/1.x、HTTP/2、WebSocket、TLS、DNS、DoH、DoT、DoQ、QUIC Initial、HTTP/3、gRPC、MQTT 能力保持不变。新增或强化：

- TLS ClientHello: JA3、JA4、SNI、ALPN、cipher suites、supported versions、signature algorithms。
- QUIC/TLS 1.3: v1/v2 Initial key derivation、CRYPTO frame、ClientHello 关联、JA3/JA4 evidence。
- Certificate Graph: leaf/SAN 关系、certificate subject/issuer 节点以及有界 chain `issued-by` 边。
- Protobuf: 有界 wire-type 元数据解码；length-delimited 内容仅保留长度与 SHA-256。
- AMQP 0-9-1: protocol header 与 frame 元数据。
- Kafka: request header、API key/version、correlation ID、client ID 与 payload hash；9092/9093 协议提示。

所有新增 parser 都有字节预算、字段/帧数量预算，并避免在分析结果中保留不透明业务 payload。

## 7. 百万级数据浏览

`VirtualTableModel` 和 `VirtualCaptureTableModel` 基于 `QAbstractTableModel`：

- `rowCount()` 可暴露百万级逻辑行数；
- 首次显示不加载全部数据；
- 按可见范围异步加载固定大小页面；
- 仅保留有界 LRU page cache；
- 相邻页预取支持虚拟滚动；
- Data 页面不再累计全部已浏览结果。

现有即时捕获模型继续使用 `QAbstractTableModel` 和有界历史窗口；大规模归档浏览走虚拟模型。
