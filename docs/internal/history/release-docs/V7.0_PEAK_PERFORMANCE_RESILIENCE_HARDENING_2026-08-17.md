## Eight-axis deep review

| Axis | Finding / risk | Hardened outcome |
|---|---|---|
| SQLite and catalogue I/O | Project listing opened one connection for the page and one more for every row. Negative SQLite limits also meant “unlimited.” | Project pages now materialize from one bounded snapshot. Task, Run, Result, Capture and Search read limits are clamped. Dashboard counters use one coherent statement. |
| Runner throughput and durability | The high-throughput result batch was conservative; increasing it alone could retain a small slow stream too long. | High mode uses a measured 96–192 row range. An independent one-second age limit flushes partial batches, including while later requests are stalled. |
| Distributed polling and lock pressure | Every Worker poll ran a full expired-lease recovery transaction. Startup and recovery contained per-Worker/per-Job query loops. | Lease recovery is single-flight and cadence-bounded. Recovery and reconciliation use grouped snapshots, while authoritative Job state and non-idempotent review rules remain unchanged. |
| Distributed health and observability | Health repeatedly scanned the Job table and exact event journal; a host booted less than 30 seconds earlier could initially expose the cache sentinel. | Live Job invariants share one grouped scan, event totals use a 30-second diagnostic cache, and the first health request always obtains real integrity and journal evidence. |
| Logging safety and write pressure | Recursive/cyclic or extremely deep logging context could exhaust the formatter; arbitrary object text could bypass inline scrubbing. | Redaction is cycle-safe, depth/item-bounded and fail-closed. Arbitrary object text is scrubbed before serialization. JSON Lines are compact and file opening is delayed until the first record. |
| Memory and resource governance | Oversized caller batches and unbounded read limits could turn streaming/local API paths into memory spikes. | Result materialization is capped at 5,000 records per transaction; catalogue/search/result pages have explicit ceilings; existing concurrency, capture and limiter bounds remain intact. |
| Security and trust boundaries | Performance changes could accidentally weaken queue receipts, lease durability, TLS identity or trust-domain separation. | FULL SQLite synchronization, WAL, 10-second busy handling, terminal receipts, HMAC throttling, TLS identity binding and trust separation are regression-gated and unchanged. |
| Release, compatibility and frozen UX | Hot-path edits can create startup/UI drift or modern-only syntax. | Python 3.8 grammar, v7.0 identity, frozen startup hashes, Welcome topology and 138-button wiring are blocking gates. A named peak-performance/resilience gate is now part of the final quality gate. |

## Paired performance evidence

Five baseline/hardened runs were interleaved in one isolated environment. The table reports medians;
it is evidence for removed hotspots, not a universal hardware promise. Raw samples are stored in
`docs/release/V7.0_PEAK_PERFORMANCE_BENCHMARK_2026-08-17.json`, and the reusable workload is
`scripts/benchmark_peak_hotpaths.py`.

| Workload | Baseline median | Hardened median | Change |
|---|---:|---:|---:|
| List 1,000 Projects | 0.476386 s / 1,001 connections | 0.004807 s / 1 connection | 98.99% lower latency; N+1 removed |
| 250 empty Worker polls | 0.057708 s | 0.034143 s | 40.83% lower latency |
| 250 dashboard snapshots | 0.143633 s | 0.133172 s | 7.28% lower latency |
| Format 20,000 structured log records | 0.344484 s | 0.310363 s | 9.90% lower CPU time |
| Representative log record | 207 bytes | 195 bytes | 5.80% less write volume |
| Persist 5,000 deduplicated results | 0.078600 s | 0.077068 s | neutral-to-improved; 5,000 correct rows |

A separate three-run end-to-end Runner sweep over 2,000 rows measured median times of 0.5226 s,
0.4193 s and 0.3552 s for batch sizes 48, 96 and 192 respectively. Batch 192 was 32.0% faster
than 48 in that workload. The time-based flush protects slow-stream durability independently.

## Native evidence still required before an absolute production peak claim

The 12 skips are the existing Qt/Windows-native environment gates, not converted failures. A final
Enterprise/LTS build must still run on supported Windows and legacy Windows lanes, then execute a
real Server plus at least two Workers across separate machines with partition, reboot, disk-full,
clock-adjustment, delayed/duplicate delivery and TLS identity-rotation drills. This source baseline
maximizes and verifies the portable hot paths without misrepresenting environment-specific evidence.
